# フロントエンドの重要導線にPlaywrightのE2Eを導入する

**日付:** 2026-09-30
**状態:** 採用
**カテゴリ:** library
**参照:** [`frontend/architecture.md` §8](../../frontend/architecture.md#8-テストvitest--react-testing-library)、[Presentation→Infrastructureの結合テストのADR](./2026-09-29-presentation-infra-integration-tests.md)（同種の判断の先例）

## 背景・経緯

`frontend/architecture.md` §8 はこれまで「E2E は将来少数（当面 Playwright 未導入）」としていた。単体・画面テスト（Vitest + RTL、API 境界は MSW）と、バックエンドの Presentation→Infrastructure 結合テストは揃ったが、フロントエンドの画面から実バックエンド・実 DB まで一気通貫で配線が噛み合っているかを確認する自動テストは無かった。

本セッションで実施した手動の探索的テスト（Playwright MCP を都度操作）で、この一気通貫の確認自体には価値があることを確認した。ただし手動操作はコードとして残らず、再現性も無い。

## 決定

- **Playwright を導入する**。対象は「止まると痛い複数画面＋接続」（`frontend/architecture.md` §8 の判断基準）に該当する、最重要の2導線に絞る
  1. 本のライフサイクル: 登録→一覧・詳細への反映→編集→削除
  2. タグのライフサイクル: 追加→本への付与→分野別集計への反映→名前変更→削除
- 内部の分岐網羅はしない（それは既存の単体・画面テストの責務のまま）。ステータスやエラーケースの網羅ではなく、「画面→API→DBの配線」を確認する
- **ローカル実行のみ。CIには載せない。** バックエンドの Presentation→Infrastructure 結合テストと同じ判断（実DB接続が要り重い）に加え、E2Eはさらに実ブラウザ・実フロントエンドサーバーも要るため、CIに載せる価値より運用コストが上回ると判断した
- テストファイルは `frontend/web/src/testing/e2e/`（`frontend/architecture.md` §6 の置き場の表に既にある「E2E 等横断テスト」の場所）
- 各テストは自分専用の本（実在するがサンプルデータと重複しないISBN）・タグを作り、テストの中で（UI操作で）後片付けする。既存の見本データ・タグには触れない
- 開発者はテスト実行前に、バックエンド（`:8080`、DB起動・migrate済み）とフロントエンド開発サーバー（`:3000`）と、バックエンドのログイン情報を入れた環境変数 `E2E_ADMIN_ID` / `E2E_ADMIN_PASSWORD`を自分で起動しておく。Playwrightからは自動起動しない（バックエンドは別リポジトリ層のプロセスで、フロントエンドのテスト設定から起動・停止の責務を持たせると密結合になるため）

## 検討した代替案

| 案 | 概要 | 却下理由 |
|---|---|---|
| A（採用） | Playwrightを導入。重要2導線のみ、ローカル実行限定 | 配線の一気通貫確認ができ、再現性・バージョン管理も得られる。範囲を絞ることでCIに載せない判断とも整合する |
| B | 何もしない（このセッションのような都度の手動確認のまま） | コードとして残らず、次に同じ確認をするたびに同じ手順を人（またはAI）が再現する必要がある |
| C | CIにE2Eを載せ、実サーバーの代わりにMSWでモックする | `frontend/architecture.md` の旧§8案（E2E環境は「導入後」CIをmock/MSW寄りにする）だったが、それではPresentation→Infrastructureの結合そのものを検証できず、既存の画面テスト（MSW前提）と重複するだけになる。今回の目的（実配線の確認）に合わない |
| D | Cypressを使う | このセッション内でPlaywright MCPの操作に既に習熟しており、追加の学習コストが無い。TypeScriptサポートも標準 |

## 判断基準（任意）

新しい重要導線（例: 単位3で今後追加する機能）ができたときに、その導線をE2Eに追加するかどうかは「止まると痛いか」で判断する。単なる画面遷移の確認や分岐網羅のためにE2Eを増やさない。
