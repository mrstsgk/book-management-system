# 管理画面の管理者トークンはログイン画面を作らず環境変数から読む

**日付:** 2026-09-30
**状態:** 採用
**カテゴリ:** architecture
**参照:** [管理画面の設計](../superpowers/specs/2026-09-30-admin-screens-design.md)、なし（口頭決定）

## 背景・経緯

書き込み系の API（本・タグの登録・更新・削除、`GET /api/catalog/{isbn}`）は `Authorization: Bearer <ADMIN_TOKEN>` を求める。管理画面（単位3）は要件定義 §3.1 でトークンを入力するログイン画面を持つ予定だったが、画面・保存先・期限切れの扱いまで作ると重く、使うのは自分1人で、デプロイもしない（要求定義 §4）。ログインは後回しにすることにした。

## 決定

- ログイン画面は作らない。frontend は環境変数 `VITE_ADMIN_TOKEN` をトークンとして使う（`web/src/lib/admin-auth.ts`）。ローカルでは `frontend/web/.env.development.local`（git 管理外）に書く
- トークンは管理画面の hook が Orval 生成フックの `request` に `adminRequest()` を渡して付ける。公開画面の要求には付けない
- トークンが空なら、管理画面の上部に設定のしかたを出し、書き込みの要求を送らない
- **この形はビルドして公開しない前提でだけ成り立つ**。Vite は `VITE_` の値を画面のコードに埋め込むので、公開すると誰でもトークンを読めて書き込める。公開するときはログイン（下の案 B）に置き換える

## 検討した代替案

| 案 | 概要 | 却下理由 |
|---|---|---|
| A（採用） | 環境変数からトークンを読む | 画面を足さずに済み、ローカルで自分だけが使う前提なら安全性も変わらない（トークンはどのみち自分の環境にある） |
| B | ログイン画面でトークンを入力し、sessionStorage に持つ | 画面・保存・誤ったトークンの扱い・ログアウトまで要り、今の使い方には重い。公開するときに入れ替える（後回し） |
| C | `mutator` で全要求に付ける | 公開画面の要求にもトークンが載る。どの要求に権限が要るかがコードから読めなくなる |

## 判断基準（任意）

画面をデプロイする、または自分以外が書き込むようになった時点で、B（または本格的な認証）に切り替える。
