# 同名への同時改名で返る 409 を版の競合として扱うことを受け入れる

**日付:** 2026-11-02
**状態:** 不採用（レビュー指摘を反映しない）
**カテゴリ:** review
**参照:** [PR #114](https://github.com/mrstsgk/book-management-system/pull/114)、[バリデーションの全件返却](./2026-11-02-validation-errors-all-at-once.md)

## 背景・経緯

タグ名の重複は相関ルール `tagNameDuplicated`（400）として、保存の前に UseCase が判定する。409 は楽観的ロックの競合（version 不一致）だけに使い、FE はタグの改名で 409 を受けたら「他で先に更新された」として一覧を取り直す。

PR #114 のセルフレビューで、2 つのリクエストがほぼ同時に別々のタグを同じ名前へ改名すると、どちらも事前の重複判定を通り、後から保存した方が DB の一意制約で 409 になるという指摘があった。このとき FE は名前の重複ではなく版の競合の文言を出す。

## 決定

この指摘は反映しない。

- 管理画面を使うのは自分 1 人で、別々のタグを同じ名前へ同時に改名する操作は現実には起きない
- 起きても DB の一意制約で同名のタグは作られず、データの整合性は保たれる。文言が実態とずれるだけで、一覧を取り直すと正しい状態が見える
- 区別して返すには、一意制約違反を `tagNameDuplicated` の 400 に変換する処理と、その経路の結合テストが要る。得られるものに対して手間が見合わない

## 検討した代替案

| 案 | 概要 | 採否・理由 |
|---|---|---|
| A（採用） | 一意制約違反は 409 のままにし、FE は版の競合として扱う | 管理者 1 人のアプリでは起きず、整合性は DB が保つ |
| B | Repository で一意制約違反を `tagNameDuplicated` の違反に変換し、400 で返す | 不採用。起きない状況のために変換とテストを足すことになり、手間に見合わない |

## 判断基準（任意）

利用者が増えて同時に編集しうる画面になったら、B を採る。事前の判定と DB の制約の間で起きる競合を、利用者に正しい理由で伝えるべきかで判断する。
