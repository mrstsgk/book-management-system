# 見本データの一言まとめ・感想をAI下書きのまま採用する

**日付:** 2026-09-30
**状態:** 採用
**カテゴリ:** review
**参照:** PR #106、[要件定義 §4.3](../specifications.md#43-動かし方運用)

## 背景・経緯

見本データ10冊の `summary`・`comment` は、それまで `（準備中）` という仮の文言だった。CodeRabbit のレビュー（PR #96・#106）で「架空の感想を入れるべきではない」という指摘を受け、いったんは本人が実際の読書体験に基づいて書くまで待つ方針にしていた。

しかし、画面の見栄え（採用担当に見せる完成度）を優先し、AIが書誌情報から作成した下書き文言に差し替えた。CodeRabbit は PR #106 で改めて「保存された `comment` はAPI応答・詳細画面に含まれ、コード内の『下書き』という注意書きは保存データには含まれない。要件定義§4.3（自分が書いた感想、架空の感想は入れない）に反する」と指摘した。

## 決定

- **指摘は妥当だが、あえて反映しない。** AI下書きの文言を見本データに採用したまま維持する
- 本人がこの決定を明示的に下した（「サンプルのコメントとして出して欲しい」）。画面の完成度を、この時点では要件§4.3の厳密な充足より優先する判断
- コード内コメント（`sample_data.go`）に「仮の下書きで、本人が実際の読書体験に基づいて書いた文章に差し替えるまで要件定義§4.3を満たさない」旨を明記し続ける。これにより、リポジトリを読む人（採用担当含む）には未充足であることが分かる
- **本人が実際に読んだ本であることは事実**（ISBN・書誌は実在確認済み）。感想の文章だけがAI下書きである
- 本人は追って実際の感想に差し替える予定。差し替えが完了するまで、この状態を「意図的な既知の未完了」として扱う

## 検討した代替案

| 案 | 概要 | 却下理由 |
|---|---|---|
| A（採用） | AI下書きの文言を採用し、ADRで理由を残す | 画面の完成度を優先。コードコメントで未充足を明示すれば、リポジトリを読む人には伝わる |
| B | CodeRabbitの提案どおり、下書きを書けない本は見本データから除外する | 見本の冊数が減り、分野の幅が示せなくなる。実際に読んだ本であることは事実なので、感想の文章だけを理由に除外するのは本末転倒と判断 |
| C | `（準備中）`のまま据え置く | 画面が「準備中」だらけになり、採用担当への見せ方として弱い |

## 判断基準（任意）

本人が実際の感想を書き終えたら、このADRの決定は「実施済み・解消」として扱ってよい（別ADRは不要。コミットで置き換えれば足りる）。次に同様の指摘（AI生成コンテンツと要件の充足）が来たときは、「画面の完成度」と「要件の厳密な充足」のどちらを優先するかを本人に確認する。
