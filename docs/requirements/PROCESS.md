# 要件定義の進め方

このリポジトリで要件定義をするときの手順。AI はこのファイルに従う。

このリポジトリはオーナー（自分）が使い手で、要件を決めるのもオーナー自身。顧客との打ち合わせは無いので、「顧客に確認する」はオーナーが判断することを指す。

要件は次の4段階で進める。全部を一度に決めず、毎回「何を決めるか」をゴールにする。

| 段階 | 中身 |
|---|---|
| 抽出 | 何をしたいか・何に困っているかを書き出す |
| 分析 | 書き出したものを論点に分け、決定・未決・調査中・保留にする |
| 仕様化 | 決定をルール・具体例・受け入れ条件にし、ストーリーにする |
| 妥当性確認 | 仕様化したもの・モックを、オーナーが OK / NG で確かめる |

## 正本は status-map.md と GitHub Issue（論点）

| ファイル | 中身 |
|---|---|
| `docs/requirements/status-map.md` | 現在地マップ：目的、機能のまとまり × 段階（業務・範囲・ルール・画面）、リリース、非機能の要件 |
| `docs/requirements/backlog.md` | ストーリーと受け入れ条件 |
| GitHub Issue（ラベル `論点`） | 論点：1論点1 Issue。タイトルは `Q-xxx 論点`。未決・調査中（ラベル）、決定（決定内容を書いて close）、保留（ラベル）。担当・期限は本文 |

調査結果は正本ではなく材料。調べたら、該当する論点の Issue に要点と推奨案をコメントする。長い調査（根拠・出典つき）だけ `docs/research/` にメモを置き、コメントからリンクする。

作業の前に `status-map.md` を読み、論点は `gh issue list --label 論点 --state all --limit 200 --json number,title,body,state,labels,createdAt,updatedAt,closedAt` で取得する（既定の件数は30件。取得した件数が上限に達したら `--limit` を増やす）。`status-map.md` を更新したら、ファイルの全文を返す（部分差分にしない）。Issue は `gh` で更新し、作成・更新・close したものを一覧で返す。

## 論点の重さと決め方

| 重さ | 決め方 |
|---|---|
| 重 | 選択肢と根拠を並べてオーナーが決める |
| 軽 | AI が案を出し、オーナーは OK / NG だけ答える |
| 実装 | 実装の都合だけで決まるもの。AI とオーナーで決めて、概要設計に理由を書く |

## 依頼ごとの動き

### 「メモを整理して」（抽出 → 分析）

1. 決定と検討を分ける。「検討する」「調査する」「〜したい（詳細未定）」は決定にせず、未決の論点にする
2. 論点の Issue のコメントと `docs/research/` の調査メモ（1行目の論点番号 Q-xxx で対応づける）を読み、まだ反映していない調査を Issue の本文の「選択肢・案」に反映する。論点の状態は変えない
3. 決定は Issue に決定内容と決定日を書いて close する。既存の決定と食い違う場合は、確認の論点を追加する
4. 新しい論点を Issue として追加する（タイトルは `Q-xxx 論点`。本文に、なぜ決める？、案、期限、まとまり）。別スコープ・将来のものはラベル `保留` を付ける
5. 範囲の増減（追加・削除）を書き出す
6. status-map.md の段階の状態を更新する

返すもの：①更新した status-map.md の全文と、作成・更新・close した Issue の一覧、②要点（5行以内）、③確認したいこと1つ。

### 「ストーリーにして」（仕様化）

1. 決定済みの論点から、`backlog.md` にストーリーを追加・更新する
2. 1ストーリーは数日で作れる大きさ。大きければ切る（作業の段階、ルールの違い、単純から複雑へ、正常系から例外へ）
3. 受け入れ条件は具体例（文字数・件数・ISBN など）で書く
4. 開発に渡せる条件（Ready）：目的がある、受け入れ条件がある、関連する未決の論点がない、画面が必要なものは合意済みのモックがある
5. Ready にできない理由は、論点として Issue に追加する

### 「進捗は？」「次どうしたらいい？」

status-map.md と未決の論点の集計から、現在地（3行）、リスク、次にやること（誰が・所要）を返す。

## 原則

- 要望をそのまま要件にしない。「それがあると何が楽になるか」を確認する
- 既にあることを理由に、判断なしで要件にしない
- オーナーの判断が必要なことを、確認なしに決めない
- DB・API・インフラの方式は要件にしない（概要設計・詳細設計で決める）
- 推測は「案」「要確認」と明示する
- 一度に渡す情報は絞る。迷っていたら「次にやることはこれだけ」に絞る

## バックログのストーリー

```markdown
### US-001 （誰）は（何を）できる
まとまり: / リリース: / 状態: 案
目的: （何が楽になるか）

受け入れ条件:
- 例：（具体的な入力・件数で）→（どうなるか）

関連する論点: Q-xxx（未決があれば Ready にしない）
画面: モック 要 / 不要（合意済みの版: ）
```
