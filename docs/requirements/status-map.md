## ① 目的

**済**。

読んだ本と、このリポジトリそのものを通じて、自分がどんなエンジニアかを採用担当・面接官に伝える。

| 受け取ってほしいこと | 何で伝わるか |
|---|---|
| 学び続けている人 | 読んだ本の分野の幅と、自分の言葉で書いた一言まとめ・感想 |
| 設計と実装がしっかりした人 | 読みやすい命名と小さな関数、依存の向きが守られた層、要件を満たす画面と API、テスト |
| チームで開発できる人 | 小さく分かれたコミット、理由の分かるコミットメッセージ、目的と確認内容が分かる PR |
| アーキテクチャを考え、AI と協業している人 | 規則と設計の文書に残した判断の理由、AI 向けの指示（`CLAUDE.md`・`AGENTS.md`）と hooks・CI による強制、レビュー指摘への対応の履歴 |

| 項目 | 内容 |
|---|---|
| 見る人 | 採用担当・面接官 |
| 渡すもの | GitHub のリポジトリだけ（公開 URL・デプロイは求めない） |
| 読まれる順（想定） | README → docs → コード・コミット・PR |
| 入口 | README。最初の画面で「何ができるか」「どう設計したか」「AI とどう作っているか」が分かり、詳しい docs へ辿れること |

アーキテクチャの考え方と AI との協業は README と docs で伝える。アプリは読書の紹介に専念させ、同じ説明をアプリ内に重複して持たない。

範囲外（不要）: 公開 URL へのデプロイと運用、複数ユーザー・ユーザー登録（書き込むのは自分だけ）、閲覧者ごとの機能（お気に入りなど）、アプリ内での設計や AI ハーネスの説明ページ。

|---|---|---|

## 非機能の要件

### コードの品質

| 要件 | 確かめ方 |
|---|---|
| 命名が言語とリポジトリの規約に沿っている | lint（Go: revive、TS: ESLint）とレビュー |
| 関数が複雑になりすぎていない | 循環的複雑度を lint で検査し、上限（10）を超えたら CI を落とす。表形式のテストは対象外 |
| 層の依存の向きが守られている（Domain は他層に依存しない） | [`backend/architecture.md`](../../backend/architecture.md) の層構成とレビュー |
| 同じ理由で変わる処理が1か所にまとまっている。似ているだけの処理は無理に共通化しない | レビュー |
| 振る舞いを変えたら、同じ場所にテストがある | CI の `Test Presence` と[テストのルール](../rules/testing.md) |
| テスト・lint・書式・脆弱性・OpenAPI と生成物のずれを CI で必ず通す | CI |

### チーム開発の進め方

| 要件 | 確かめ方 |
|---|---|
| コミットは1つの論理的な変更ごとに分け、それぞれ単体でビルドできる | [コミットのルール](../rules/git-commit-message.md)とレビュー |
| コミットメッセージに、何をしたかと、必要ならなぜそうしたかが書かれている | 同上 |
| PR のタイトルと本文から、ゴールとマージ前に確かめたことが分かる | [PR のルール](../rules/git-pull-request.md)とテンプレート |
| レビュー指摘は指摘ごとにコミットし、スレッドにコミット ID で返信する | 同上 |
| 自明でない判断の理由を、規則・設計の文書の該当箇所に残す | レビュー |

### 動かし方・運用

| 要件 | 確かめ方 |
|---|---|
| README の手順だけで、ローカルに見本データ入りの画面を立ち上げられる | README の手順どおりに起動して確かめる |
| 書き込みはログイン済みのセッションで守る。ID・パスワードが未設定ならログインできない。閲覧は認証なし | API のテスト |
| 外部カタログの規約（openBD は本の紹介目的に限る）を守る | 画面の確認 |
