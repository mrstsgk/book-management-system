# 要求定義

このリポジトリで何を作るか、なぜ作るかの正。どう作るかは [`architecture.md`](./architecture.md) 以下の各文書に書く。

## 1. 目的

読んだ本と、このリポジトリそのものを通じて、自分がどんなエンジニアかを採用担当・面接官に伝える。

- 読んだ本と感想から、**学び続けている人**であることを伝える
- 設計・実装・テスト・CI から、**設計と実装がしっかりした人**であることを伝える
- ADR・`CLAUDE.md`・hooks・PR の進め方から、日々**どんなソフトウェアアーキテクチャを考え、AI とどう協業し、ハーネスをどう作っているか**を伝える

## 2. 見る人と見せ方

| 項目 | 内容 |
|---|---|
| 見る人 | 採用担当・面接官 |
| 渡すもの | **GitHub のリポジトリだけ**（公開 URL・デプロイは求めない） |
| 読まれる順（想定） | README → 画面のスクショ → ADR・docs → コード |
| 入口 | README。最初の画面で「何ができるか」「どう設計したか」「AI とどう作っているか」が分かり、詳しい docs へ辿れること |

アーキテクチャの考え方と AI との協業は **README と docs** で伝える。アプリは読書の紹介に専念させ、同じ説明をアプリ内に重複して持たない。

## 3. 機能要求

### 3.1 読んだ本が持つ情報

| 項目 | 入手元 | 要求 |
|---|---|---|
| ISBN | 自分で入力 | 同じ本は二重に登録できない |
| 書名・著者・出版社・出版日 | 外部カタログ（openBD、無ければ楽天ブックス） | 自動で取得する |
| 書名の上書き | 自分で入力（任意） | 外部カタログの書名が実際と違うときに、自分で正しい書名にできる。上書きした書名は、外部カタログを取り直しても消えない |
| 書影 | 外部カタログの URL | 画像は保存しない。楽天の書影を表示するときはクレジットを表示する |
| Amazon リンク | ISBN から導出 | 保存しない |
| 一言まとめ | 自分で入力 | 一覧で見せる短い要約 |
| 感想 | 自分で入力 | 詳細で見せる本文 |
| 評価 | 自分で入力 | 1〜5 |
| 分野タグ | 定義済みのタグから選ぶ | 1冊に複数付けられる |

価格・出版状況・著者の個別管理は持たない。

### 3.2 分野タグ

- タグは自分が先に定義し、本にはその中から選んで付ける（表記ゆれを防ぐ）
- タグの追加・名前の変更・削除ができる

### 3.3 公開画面（誰でも見られる）

| 画面 | 要求 |
|---|---|
| 一覧 | 書影・書名・一言まとめ・評価・分野タグを並べる。分野タグで絞り込める |
| 詳細 | 書誌・書影・Amazon リンク・一言まとめ・感想・評価・分野タグを見せる |
| 分野別の集計 | 分野タグごとの冊数を見せ、学んでいる分野の幅が一目で分かる |

PC で見ることを主とし、スマホでも崩れない程度にする。

### 3.4 管理画面（自分だけ）

| 画面 | 要求 |
|---|---|
| ログイン | 管理者トークンを入力する（ユーザー管理は持たない） |
| 本の登録 | ISBN を入れて外部カタログの書誌・書影を確かめてから、一言まとめ・感想・評価・分野タグを添えて登録する |
| 本の編集・削除 | 書名の上書き・一言まとめ・感想・評価・分野タグを変える。削除できる |
| タグの管理 | タグの追加・名前の変更・削除 |

### 3.5 見本データ

- 実際に読んだ4冊を、自分が書いた感想・分野タグ付きで見本データとしてリポジトリに持つ（架空の感想は入れない）
  - データ指向アプリケーションデザイン（9784873118703）
  - 改訂新版 良いコード／悪いコードで学ぶ設計入門（9784297146221）
  - 徹底攻略 AWS認定 SAA 教科書 第3版（9784295016090）
  - プロダクトマネジメントのすべて（9784798166391）
- ローカルで起動したとき、データが空なら自動で投入する
- 投入は外部カタログに頼らない（ネットが無い環境や外部カタログの障害でも起動できるように、書誌も見本データに持つ）

## 4. 非機能要求

| 項目 | 要求 |
|---|---|
| 動かし方 | ローカルで起動できればよい（README の手順で、見本データ入りの画面が見られる） |
| 認証 | 書き込みは管理者トークンだけで守る。閲覧は認証なし |
| 外部カタログ | 規約（openBD は本の紹介目的に限る、楽天はクレジット表示）を守る |
| 品質 | テスト・lint・OpenAPI とフロントの型のずれ検知を CI で必ず通す |
| 設計の記録 | 自明でない判断は ADR に残す（[ADR のルール](./rules/adr.md)） |

## 5. やらないこと

- 公開 URL へのデプロイと運用
- 複数ユーザー・ユーザー登録
- 画像の保存（書影は提供元の URL をそのまま使う）
- アプリ内での、設計や AI ハーネスの説明ページ（README と docs で伝える）

## 6. 実現の単位と順序

各単位は、設計 → 実装計画 → 実装の順に進める。既存の #58〜#60（読んだ本の API）はこの要求の土台として、そのままマージする。

| 順 | 単位 | 中身 |
|---|---|---|
| 1 | バックエンド拡張 | 書名の上書き、一言まとめ、分野タグ（定義と本への付与）、分野別の集計、起動時の見本データ投入 |
| 2 | 公開画面 | 一覧（分野タグで絞り込み）、詳細、分野別の集計 |
| 3 | 管理画面 | ログイン、本の登録・編集・削除、タグの管理 |
| 4 | README・docs | 採用担当の入口にする。画面のスクショ、設計の方針、AI との協業とハーネスを案内する |

単位4は文章から先に進めてよい（スクショは画面ができてから足す）。

文字数などの細かい制約は、各単位の設計で決める。
