# 要求定義

このリポジトリで**誰に何を伝えるために作るか**の正。システムが満たすべきことは [`specifications.md`](./specifications.md)（要件定義）に、どう作るかは [`architecture.md`](./architecture.md) 以下の各文書に書く。

## 1. 目的

読んだ本と、このリポジトリそのものを通じて、自分がどんなエンジニアかを採用担当・面接官に伝える。

- 読んだ本と感想から、**学び続けている人**であることを伝える
- 設計・実装・テスト・CI から、**設計と実装がしっかりした人**であることを伝える
- ADR・`CLAUDE.md`・hooks・PR の進め方から、日々**どんなソフトウェアアーキテクチャを考え、AI とどう協業し、ハーネスをどう作っているか**を伝える

## 2. 見る人と見せ方

| 項目 | 内容 |
|---|---|
| 見る人 | 採用担当・面接官 |
| 渡すもの | **GitHub のリポジトリだけ**（公開 URL・デプロイは求めない） |
| 読まれる順（想定） | README → 画面のスクショ → ADR・docs → コード・コミット・PR |
| 入口 | README。最初の画面で「何ができるか」「どう設計したか」「AI とどう作っているか」が分かり、詳しい docs へ辿れること |

アーキテクチャの考え方と AI との協業は **README と docs** で伝える。アプリは読書の紹介に専念させ、同じ説明をアプリ内に重複して持たない。

## 3. 成功の基準

見終えた採用担当が、次のように受け取れること。

| 受け取ってほしいこと | 何で伝わるか |
|---|---|
| 学び続けている人 | 読んだ本の分野の幅と、自分の言葉で書いた一言まとめ・感想 |
| 設計と実装がしっかりした人 | 読みやすい命名と小さな関数、依存の向きが守られた層、要件を満たす画面と API、テスト |
| チームで開発できる人 | 小さく分かれたコミット、理由の分かるコミットメッセージ、目的と確認内容が分かる PR |
| アーキテクチャを考え、AI と協業している人 | ADR に残した判断、AI 向けの指示（`CLAUDE.md`）と hooks による強制、レビュー指摘への対応の履歴 |

## 4. やらないこと

- 公開 URL へのデプロイと運用
- 複数ユーザー・ユーザー登録（書き込むのは自分だけ）
- 閲覧者ごとの機能（お気に入りなど）
- アプリ内での、設計や AI ハーネスの説明ページ（README と docs で伝える）

## 5. 実現の単位と順序

各単位は、設計 → 実装計画 → 実装の順に進める。既存の #58〜#60（読んだ本の API）はこの要求の土台として、そのままマージする。

| 順 | 単位 | 中身 |
|---|---|---|
| 1 | バックエンド拡張 | 書名の上書き、一言まとめ、分野タグ（定義と本への付与）、分野別の集計、キーワード検索、起動時の見本データ投入 |
| 2 | 公開画面 | 一覧（検索・分野タグで絞り込み・ページング）、詳細、分野別の集計 |
| 3 | 管理画面 | ログイン、本の登録・編集・削除、タグの管理 |
| 4 | README・docs | 採用担当の入口にする。画面のスクショ、設計の方針、AI との協業とハーネスを案内する |

単位4は文章から先に進めてよい（スクショは画面ができてから足す）。複雑度の lint（[要件定義 §4.1](./specifications.md#41-コードの品質)）は単位1の最初に入れる。
