# 管理画面（単位3）の設計

**日付:** 2026-09-30
**参照:** [要件定義 §3](../../specifications.md#3-管理画面自分だけ)、[画面イメージ](../../design/admin-screens/README.md)、[ADR](../../adr/2026-09-30-admin-token-from-env.md)

自分だけが使う書き込み用の画面（本の一覧・登録・編集・削除、タグの管理）を `frontend/web` に作る。見た目は画面イメージを、振る舞いは要件定義 §3 を正とする。API は揃っているので、バックエンドは変えない。

## ログインは後回し

> 2026-09-30: [ログインの設計](./2026-09-30-admin-login-design.md) で置き換えた。以下は当時の判断。

- ログイン画面は作らない（要件定義 §3.1 を「後回し」に改める）。書き込み系 API に付ける管理者トークンは、frontend の環境変数 `VITE_ADMIN_TOKEN` から読む。ローカルでは `frontend/web/.env.development.local`（git 管理外）に書く（値はバックエンドの既定 `local-admin-token`。手順は `frontend/README.md`）。リポジトリに既定値のファイルは置かない
- トークンは画面のコードに埋め込まれるので、ビルドして公開すると誰でも書き込める。デプロイしない前提（要求定義 §4）でだけ成り立つ。判断は ADR に残す
- トークンは管理画面の hook から Orval 生成フックの `request: { headers }` で渡す（`lib/admin-auth.ts` の `adminRequest()`）。`mutator` で全要求に付けない（公開画面の要求にトークンを載せないため）
- `VITE_ADMIN_TOKEN` が空なら、管理画面の上部に「管理者トークンが設定されていません（`frontend/web/.env.development.local` に `VITE_ADMIN_TOKEN` を書く）」を出し、書き込みボタンを押せないようにする

## 画面と URL

| 画面 | path | 使う API |
|---|---|---|
| 本の一覧（管理） | `/admin` | `GET /api/books`（公開と同じ一覧。「もっと見る」も同じ） |
| 本の登録 | `/admin/books/new` | `GET /api/catalog/{isbn}`、`GET /api/tags`、`POST /api/books` |
| 本の編集・削除 | `/admin/books/:id/edit` | `GET /api/books/{id}`、`GET /api/tags`、`PUT /api/books/{id}`、`DELETE /api/books/{id}` |
| タグの管理 | `/admin/tags` | `GET /api/tags/counts`、`GET /api/tags`、`POST`・`PUT`・`DELETE /api/tags…` |

- 管理画面は公開画面と別のレイアウト（黒いヘッダーに「管理」の印、ナビ「本」「タグ」、「公開画面を見る」）。公開画面のヘッダーから管理画面へのリンクは置かない（採用担当が迷い込まないように）
- 本の一覧（管理）は表（書名・評価・分野タグ・一言まとめが「（準備中）」かどうか・「編集」）

## 本の登録・編集（同じフォーム）

- 登録: ISBN を入れて「確かめる」で `GET /api/catalog/{isbn}` を呼び、書誌と書影（openBD に無ければ「書影なし」の枠）を出す。404 は「外部カタログに見つかりませんでした」
- 入力欄は1画面に置く（段階式にしない）。書名の上書き（任意・255字）、一言まとめ（必須・100字）、感想（必須・5000字・改行可）、評価（1〜5 のラジオ）、分野タグ（チェックボックス・10個まで）。文字数の表示を添える
- 送信前に同じ上限をフロントでも確かめ、誤りは上部の要約（各項目へのリンク）と項目ごとの文言で出す。サーバーの 400 の `errors[{field, rule}]` も同じ場所に出す（`field` は JSON 名）
- 登録の 409 は「この ISBN の本はすでに登録されています」、カタログに無い 400 は「この ISBN の本は外部カタログに見つかりませんでした」
- 編集は `GET /api/books/{id}` で初期値を入れる。分野タグは名前で返るので、`GET /api/tags` の名前から ID に引き直す。保存は `version` 付きの `PUT`。409 は「ほかの画面で先に更新されていた」注意と「最新を読み込む」（取り直してフォームを入れ直す）
- 削除は確認ダイアログ（書名を出す）で確定したときだけ `DELETE`。成功したら `/admin` へ戻り、「『書名』を削除しました」を出す
- 登録・保存に成功したら `/admin` へ戻り、完了のお知らせを出す。お知らせは遷移の state で渡す（Zustand を使わない）

## タグの管理

- 一覧は `GET /api/tags/counts`（冊数付き）と `GET /api/tags`（冊数0のタグも出すため）を名前で合わせ、名前順に並べる
- 追加・名前の変更は、その場の入力欄。同名の 409 は「『名前』というタグはすでにあります」。変更は `version` 付き、409（先に更新）は一覧を取り直して伝える
- 削除は確認ダイアログ（「付いている N 冊から外れます。本は消えません」）

## 共通の部品（`components/`）

- `ConfirmDialog`（`<dialog>` と `showModal()`、開いたらキャンセルにフォーカス、Esc で閉じる）: 本の削除とタグの削除で使う
- `FormField`（ラベル・必須/任意・入力・文字数・エラー文言を `aria-describedby` で結ぶ）と `ErrorSummary`: 本のフォームとタグの入力で使う
- `ApiError` に `fieldErrors: { field: string; rule: string }[]` を足す（`mutator` が `ErrorResponse.errors` を詰める）

## テスト

`frontend/architecture.md` §8 と `docs/rules/testing.md` に従う。API は生成 MSW ハンドラを上書きし、書き込みの要求に `Authorization: Bearer <token>` が付くことも確かめる。

- 純関数は単体: フォームの検証（各上限ちょうどと+1、空白だけは未入力）、サーバーの `errors` を項目の文言に変える関数、タグ名→ID の引き直し、タグ一覧の合わせ方
- 画面ごとに: 読み込み中 / 成功 / API エラー→再試行、各 4xx の文言、送信中はボタンを押せない、失敗しても入力が消えない、ダイアログのキャンセルでは API を呼ばない
- `VITE_ADMIN_TOKEN` が空のときの注意と、書き込みボタンが押せないこと

## やらないこと

- ログイン（後回し）
- 管理画面の検索・絞り込み（冊数が少ないため。公開の一覧で足りる）
- 楽天の削除指示の画面（楽天は撤去済み）
