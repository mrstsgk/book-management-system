# 判断記録（ADR）のルール

## なぜ「Architecture」ではなく「Any」か

一般的な ADR はアーキテクチャ上の選択だけを記録する。本ルールでは ADR の「A」を **Any** と読み替え、アーキテクチャに限らず **自明でない判断すべて**（ライブラリ・インフラの選定、見送ったレビュー指摘、デバッグでの根本原因の判断など）を記録対象にする。

判断記録の目的は、**あとから「なぜ」を再構成するのに必要な事実** — その時点で真だった前提、検討した選択肢、結論 — を残すこと。対象を「アーキテクチャ」に限定するのは恣意的な線引きで、将来の読み手（人でも AI でも）が実際に必要とする判断の大半を捨ててしまう。どのライブラリをなぜ却下したか、lint / レビュー指摘をなぜあえて反映しなかったか、バグの原因をなぜより目立つ Y ではなく X と判断したか — いずれもコードには残らず、コミットメッセージにも収まりにくい。

放置すると起きる2つの失敗と、その対策:

1. **記録が古くなる／書かれなくなる** — 記録を強制するものが無いと、判断した本人が離れた時点で習慣が崩れる。下記「ADR ファイルが必須になる条件」を機械的に確認できる程度まで具体化し、機械的に検知できるトリガー（依存・インフラファイルの変更）に対応する `docs/adr/` が無ければ `require-adr-on-decision.sh` が完了をブロックする
2. **「ADR」と「ただのバックログ」の境界がぼやける** — 何でも対象にすると何も対象でなくなり、誰も読まないノイズになる。「将来の読み手が『なぜ A でなく B なのか』と問いそうか、かつ他の何もそれに答えていないか」という意図的に狭いテストで絞る。日常的・可逆的・既に文書化済みの選択は対象外

記録の形式は意図的にゆるくしてある（必須は背景と結論のみ）。採否（採用 / 不採用 / 保留）の欄を設け、却下した案も採用した案と同じように見つけられるようにする。

## 機能単位の設計ドキュメントとの関係

機能の設計中に決めた機能スコープの判断（`docs/` 配下の spec・実装計画ドキュメント等）は、そのドキュメント自身の「設計判断」節に書き、ここには書かない。`docs/adr/` は1機能を超える・またはまたがる判断だけを置く: アーキテクチャ、ライブラリ・依存・インフラの選択、見送ったコードレビュー指摘、実際に複数案があった中でのデバッグの根本原因判断。

## ADR ファイルが必須になる条件

次のいずれかが起きたら `docs/adr/YYYY-MM-DD-<slug>.md` を作成する。

1. ライブラリ・依存・インフラツールの追加・置き換え・削除（真剣に検討した上で **採用しない** と決めた場合も含む）
2. `superpowers:systematic-debugging` が、複数の実在する選択肢の中から根本原因と修正方針を選んで結論に至った
3. CodeRabbit / コードレビューの指摘を、「同意しない」以上の理由で意図的に **反映しない**
4. その他、将来の読み手が「なぜ A でなく B なのか」と問いそうで、コード・テスト・コミットメッセージだけでは答えられない判断

些細な選択や簡単に戻せる選択は不要。あらゆる細かい判断のログではない — 何でも書くことこそが、上記の「古くなる」「バックログとの境界がぼやける」問題を生む。

## 形式

1判断1ファイル。連番ではなく日付で命名する（連番は並行する worktree 間で衝突するが、日付は衝突しにくい）。

```
docs/adr/YYYY-MM-DD-<slug>.md
```

```markdown
# <タイトル>

**日付:** YYYY-MM-DD
**状態:** 採用 / 不採用 / 保留
**カテゴリ:** architecture / library / infra / debug / review
**参照:** Issue/PR/spec へのリンク（無ければ「なし（口頭決定）」）

## 背景・経緯

なぜこの判断が必要になったか。

## 決定

何を決めたか（採用・不採用どちらも書く）。

## 検討した代替案（あれば）

| 案 | 概要 | 却下理由 |
|---|---|---|
| A（採用） | ... | ... |
| B | ... | ...のため却下 |

## 判断基準（任意）

次に似た判断をするとき何を優先するか。一般化できる基準があれば書く。
```

- 議論した Issue / PR / spec へリンクする。ここには議事録ではなく結論と「なぜ」を書く（詳細はリンク先にある）
- **不採用の判断も必ず記録する**。何を試してなぜダメだったかは採用した案と同じくらい価値があり、しかも最も失われやすい

## 探し方

中央の索引は置かない。`ls docs/adr/` か `grep -rl <keyword> docs/adr/` で探す。索引ファイルは古くなる場所が1つ増えるだけなので不要。

## 強制の仕組み

「ADR ファイルが必須になる条件」の4つのうち、差分だけで検知できるのは条件1（依存・インフラの変更）だけ。hook は `go.mod` / `package.json` が変わったことは分かるが、デバッグが根本原因の判断で終わったことや、レビュー指摘が正当な理由で見送られたことは分からない。そのため、確認できる範囲で分担する。

- **`.claude/hooks/require-adr-on-decision.sh`（Stop・ブロックあり）** — 条件1のみ。依存・インフラのトリガーファイル（`go.mod` / `go.sum`、`package.json` / `pnpm-lock.yaml`、`Dockerfile` / `Dockerfile.api`、`.github/workflows/*.yml`、`infrastructure/**/*.tf`）が変わったのに同じ差分で `docs/adr/` 配下が1つも変わっていない場合、または変更した `docs/adr/*.md` の `## 背景・経緯` か `## 決定` が空・プレースホルダのままの場合に完了をブロックする。確認するのは **構造的な完全性のみ**（必須見出しが空でないこと）で、内容の妥当性は見ない（grep ベースの検査の限界）。誤検知（判断を伴わないパッチ版の lockfile 更新など）は `SKIP_ADR_CHECK=1` で回避する
- **`.claude/hooks/adr-reminder.sh`（Stop・ブロックなし）** — 条件2と3。直近のユーザー発言以降に `superpowers:systematic-debugging`、`code-review:code-review` / `coderabbit:coderabbit-review` が使われていれば、ターン終了時（根本原因の判断や指摘の見送りが実際に決まった後）に、該当すれば記録するようリマインドする。スキル呼び出し直後（PostToolUse:Skill）ではまだ判断が確定していないため、Stop で確認する。そのスキル実行が記録に値する判断を生んだかは判定できないため、ブロックはしない。判断はスキルを実行した本人（人でも AI でも）に委ねる
- **条件4**（その他の判断）には hook が無い。上記の「将来の読み手はなぜと問うか」テストを人／AI が適用する以外に拾う方法は無く、`CLAUDE.md` の hook の無い他のルールと同じく、本ルールが読まれ守られることに依存する
