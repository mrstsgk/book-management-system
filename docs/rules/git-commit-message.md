# コミットメッセージ規約

本プロジェクトのコミットメッセージ規約。後から履歴を追う際の一貫性と検索性のため、すべてのコミットで以下に従う。

## フォーマット

```text
<type>: <subject>

<body>（オプション）
```

- **type**: コミットの種類（必須）
- **subject**: 変更内容の簡潔な説明（必須、**最大 50 文字**）
- **body**: なぜその実装をしたのか、実装経緯の詳細説明（任意、経緯がある場合は推奨）

## Type 一覧（ブランチ運用のプレフィックスと同義）

| Type | 説明 | 例 |
|------|------|-----|
| `feat` | 新機能追加 | `feat: 書籍登録APIを追加` |
| `fix` | バグ修正 | `fix: 著者の書籍一覧で重複レコードが表示される問題を修正` |
| `chore` | 雑務（CI / ビルド / 環境設定など） | `chore: CIにgolangci-lintを追加` |
| `refactor` | リファクタリング | `refactor: 変数名をauthorIDsに変更` |
| `test` | テスト追加・修正 | `test: UpdateBookUsecaseにテストを追加` |
| `hotfix` | 緊急バグ修正（本番） | `hotfix: 書籍更新時の致命的なバグを修正` |

## Subject ルール

- **最大 50 文字**
- **日本語必須**（subject・body ともに日本語を使用）
- **過去形ではなく現在形**：「追加した」ではなく「追加」
- **句点不要**

## コミットの粒度

後から人が見て「何をした作業か」がわかる単位で分割する。レビュー・調査・revert がしやすい履歴を重視する。

- 機能追加・バグ修正・リファクタリング・テスト追加などは別コミットに分ける
- 1 コミット = 1 つの論理的な変更単位（説明文が 1〜2 文で書ける範囲）
- 巨大な一括コミットや、関係ない変更が混じったコミットは避ける

## Body を書くべき場合

- 背景や実装理由を残したい場合
- 複雑で後から見て理解しづらい変更
- 複数案から選択した理由を残したい場合
- バグの原因や再現条件を記録したい場合
