# プルリクエスト運用ルール

本プロジェクトの PR 運用ルール。レビューフローの効率化と一貫性のため、PR 作成・マージ時は以下に従う。


## レビュー分類の決定（AIが提案し、人が選ぶ）

PRを作成するAI（Claude Code / Codex等）が変更内容を確認し、分類と理由を提案する。**人が決定するまでPRの作成・分類ラベルの付与を待つ**。コード・テスト・PR本文の準備は先に済ませる。CodeRabbit自身が作成前に質問する仕組みではない。

| 人が選ぶ分類 | ラベル | profile | 主な観点 |
|---|---|---|---|
| 設計・仕様 | `review:design` | `assertive` | 責務・依存方向・仕様の整合性・例外ケース |
| 通常の実装 | `review:standard` | `chill` | 合意済み設計との一致・不具合・境界値・テスト漏れ |
| 重要な実装 | `review:critical` | `assertive` | 上記に加えて異常系・同時実行・冪等性・権限・データ整合性 |
| CodeRabbit のレビュー不要 | `review:skip` | — | CodeRabbit の自動レビューを行わない。人のレビュー承認・CI などのマージ条件は変わらない |

- 4つから**必ず1つ**選ぶ。通常にもラベルを付け、未分類と区別する。モック・保守・運用設定・資料変更も目的と影響に応じて提案し、人が選ぶ。資料があるという理由だけで設計扱いにしない。
- 認証・セッション・既存データに影響する移行・外部カタログ連携などは「重要な実装」を推奨する。ファイル名・ブランチ名だけで確定しない。
- 質問例: 「今回はログインのセッション処理を変更するため、③重要な実装を推奨します。①設計・仕様 / ②通常の実装 / ③重要な実装 / ④CodeRabbitのレビュー不要のどれでPRを作成しますか？」
- 無回答・単なる「PRを作って」を分類への同意として扱わない。同じPRについて明示的に決定済みなら再質問しない。
- 「お任せ」「assertiveで進めて」など判断を明示的に委任された場合は、その範囲でAIが分類し、再質問せず進める。PR本文には人の委任内容とAIの判断理由を分けて記録する。実装をassertiveで確認する場合は `review:critical` とし、未実装の免除がある `review:design` を強度調整のためだけに使わない。工程変更時も委任がその変更を含むか確認し、範囲外なら質問する。
- 人が選んだ分類・理由・決定者と確認記録をPR本文に記載する。AIの推薦を人の決定として記録しない。明示的な委任がある場合は上記の記録で代える。

### 作成からレビュー開始まで

1. AIが差分を調べて質問し、人が分類を決める。
2. AIがPRを**まずDraftとして作成**し、決定した分類ラベルを1つ付け、付与結果を確認する。APIではPR作成とラベル付与が別操作になるため、未分類のままレビューを始めない。
3. 設計PRはDraftのままレビューする。通常・重要な実装は準備が整ってからReadyにする。人へのレビュー依頼の条件は従来どおり。
4. `review:skip` 以外では、CodeRabbitのレビューが開始されたことと、適用設定を確認する。ラベル付与だけで必ず再レビューされるとは限らないため、開始しない場合はPRで `@coderabbitai full review` を依頼する。`review:skip` では自動レビューが開始しないのが正常で、依頼しない。`@coderabbitai configuration` でprofile・auto_review・工程別指示を確認する。

### 設計から実装へ移る場合

同じDraft PRに実装を追加する前に、AIが通常/重要のどちらかを提案し、人が選び直す。既存分類を外してから新しい分類を付け、本文の決定記録と合意済み設計へのリンクを更新する。他用途のラベルは変更しない。実装が揃ってからReadyにし、最新の分類で全体レビューを依頼する。作成後の分類変更も同じ手順で行う。

設計時には未実装・未生成・実装テスト未追加そのものを指摘させない。この免除は設計レビュー中だけであり、実装をマージする際の既存テスト・生成物・CI要件は変わらない。実装時は、具体的な不具合または要件・リポジトリ規則違反がある場合に限り合意済み設計の変更を提案する。

### 設定と確認

- 設定の正本はルートの `.coderabbit.config.ts`。優先される `.coderabbit.yaml` / `.coderabbit.yml` を併置しない。
- 未分類・分類重複は自動レビューを停止する。CI `Review Policy / classification` も失敗する。人に確認して1つに修正する。CIはラベル数を検査するもので、人の回答の真正性までは検証しない。
- CodeRabbitによるラベルの自動付与は無効。ヒアリングの実施はAI向けルールとPR本文の記録で運用する。
- 設計ラベルのみDraftの自動レビューを有効化する。ローカルCLIなどPR情報が無い場合は `chill` とし、人の分類とみなさない。PRの分類連動レビューはCodeRabbitのGitHub連携で確認する。
- ローカル確認: `.mise.toml` の Node で、ルートにて `npm ci --ignore-scripts` → `npm run typecheck` → `npm test`。フロントエンドのpnpm環境とは別のレビュー設定専用ツール。
- CodeRabbit の自動レビューが始まらないとき（ベースが `develop` / `main` 以外の積み上げた PR、無料枠の上限など）は、PR で `@coderabbitai full review` を依頼する。それでも受けられないときは、AI のセルフレビュー（Claude Code の `/code-review`）で代え、見つかった指摘と対応を PR に記録する。指摘への対応の仕方は下の「レビュー指摘対応」と同じ。
- `Review Policy` をマージ必須にする場合は、ブランチ保護に `classification` と `config` のチェックを登録する。ワークフローの追加だけでブランチ保護が変更されるわけではない。

### 初回導入

分類ラベルが存在しない場合は次を実行する。既存ラベルは上書きしない。

```sh
gh label create 'review:design' --color '7057ff' --description '人が決定: 設計・仕様 / assertive'
gh label create 'review:standard' --color '0e8a16' --description '人が決定: 通常の実装 / chill'
gh label create 'review:critical' --color 'b60205' --description '人が決定: 重要な実装 / assertive'
gh label create 'review:skip' --color 'cccccc' --description '人が決定: CodeRabbit の自動レビューなし / 人の承認・CI は必要'
```

導入PRではまず設定の型チェックと分岐テストを通す。実際のGitHub連携については、設定が適用されたレビューで3分類のprofile、設計Draftのレビュー、分類変更後の全体レビューを確認する。ローカルテスト通過だけで外部連携の確認済みとはしない。

## マージ条件

- 最低 1 人のレビュー承認が必要
- CI（GitHub Actions）が全て成功している
- 人が決めたレビュー分類が本文に記録され、対応する分類ラベルが1つ付いている（`Review Policy` 通過）
- コンフリクトが解消されている
- ベースは `develop` ブランチへマージ（`hotfix/*` のみ `main`。[ブランチ運用ルール](./git-branch.md) 参照）
- マージ後はブランチを削除

## レビュー指摘対応

レビューの指摘に対応する際は、対応の追跡性とレビュアーの再確認を容易にするため以下に従う。

- **CodeRabbit の指摘は、対応する前に一度、敵対的に吟味する**：指摘は正しい前提では受け取らず、「本当に対応が必要か」を疑って検証してから、対応するかを決める。見るのは次の点。
  - 現在のコードで本当に起きるか（指摘が古い、または前提の読み違いではないか。可能なら違反を実際に入れて再現する）
  - この PR のスコープと、リポジトリの規則・仕様に根拠があるか（一般論や好みだけの指摘ではないか）
  - 直す手間と、直して得られるものが見合うか
  - CodeRabbit が「Unverified」などと断っている指摘は、とくに裏取りを先に行う
- 吟味の結果、**妥当なら対応する**。妥当でない・不要なら対応せず、その理由を同じスレッドに返信する。疑うのは検証のためで、指摘を却下するためではない（極端に対応しない姿勢にはしない。吟味して妥当だったものは素直に直す）。
- **指摘ごとにコミットを分ける**：1 つの指摘対応 = 1 コミット。複数の指摘をまとめてコミットしない。
- **指摘のスレッドにリプライする**：対応した指摘ごとに、該当コミットの **コミット ID** と **対応内容** をそのスレッドへコメントする。CodeRabbit の指摘も同様に扱う。
  - スレッド返信可能なレビューコメント（行に紐づく review comment）は `gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies -X POST -f body='<返信本文>'` でそのスレッドへ返信する。新規の PR コメントとして書き起こさない。
  - 行に紐づかない全体コメント（walkthrough 等）でスレッド返信ができない場合のみ、通常の `gh pr comment` で返信してよい。

## PR テンプレート

実体は `.github/pull_request_template.md`（PR 作成時に GitHub が自動挿入する）。内容は以下と同一に保つ。

````markdown
<!-- type: feat / fix / chore / docs / refactor / test / hotfix -->
<!-- ベースブランチ: 通常は develop（hotfix/* のみ main） -->

## 参照

<!-- 参照しているIssueや関連するプルリクエスト・Issueのリンクを貼る -->

<!-- refs: #123 -->

## ゴール

<!-- 何の機能ができていればゴールか（UI がある場合は、どの画面ができていればゴールか）を書く -->
<!-- 「何を変えたか」の要約は書かない（CodeRabbit が自動でまとめる） -->

## レビュー分類

<!-- AIが変更内容と推奨理由を提示し、人が決定してからPRを作成する。未回答を通常扱いにしない。 -->
<!-- review:design（設計・仕様/assertive）、review:standard（通常の実装/chill）、review:critical（重要な実装/assertive）、review:skip（CodeRabbitの自動レビューなし。人のレビュー承認・CIは必要）から1つ。 -->
- 分類・ラベル:
- 判断理由:
- 決定者・確認記録: <!-- 人の名前と回答内容、または決定を確認できるリンク。AIの推薦を人の決定として書かない -->
- 合意済み設計: <!-- 実装の場合は設計資料・PRへリンク。該当しない場合はN/Aと理由 -->

## 確認事項

<!-- AI / 作成者向け: マージ前にこの PR 単体で担保できることだけ書く。 -->
<!-- 書いてよい: ローカル動作確認、ローカルUI確認、追加・変更した自動テスト、CI -->
<!-- 書いてはいけない: stg/prd 手動確認、デプロイ後確認、結合テスト計画 -->
<!-- 自動テストの担保・ローカル確認済みは、証拠画像（テスト結果・画面キャプチャ等）があれば添付する（必須ではない） -->

- [ ] バックエンド: 追加・変更した自動テストで動作担保済み（対象外なら N/A）
- [ ] フロントエンド: 追加・変更した自動テストで動作担保済み（対象外なら N/A）
- [ ] ローカルで確認済み（動作、UI がある場合は画面表示も）
  <!-- 何をどう確認したか（テストした操作・入力・画面）を具体的に書く。画像は任意、確認内容の記述は必須 -->
  -
- [ ] CI 通過
````

## 「確認事項」に書いてよいこと / 書いてはいけないこと

PR 本文の「確認事項」は **この PR をマージしてよいかを判断する材料** である。チェックされないまま Close されて意味がない項目（デプロイ後・stg 手動など）は書かない。

| | 内容 |
| --- | --- |
| **書いてよい** | ローカルでの動作確認、ローカルでの UI 確認（画面変更がある場合）、追加・変更した自動テストの通過、CI 通過 |
| **書いてはいけない** | stg / prd での手動確認、デプロイ後の確認、リリース後の結合テスト、本番監視 |

**AI 向け:** PR 本文を作成・編集する際は、セクション名を `## 確認事項`（`動作確認` / `テスト計画` ではなく）とする。マージ前に PR 単体で担保できる検証のみを列挙する（該当する場合はバックエンド/フロントエンドの自動テスト担保を別チェックボックスに分ける、ローカル確認、CI）。stg/prd の手動確認やデプロイ後 TODO をチェックリストに追加しない。ローカル確認項目には、何を確認したか（操作・入力・画面）を必ず具体的に記述する（画像添付は任意）。UI に影響がない PR では動作確認のみで良く、画面確認の記述は不要。自動テスト項目にも有用であれば証拠画像を添付してよい（必須ではない）。

## 記載のポイント

- 簡潔に、しかし後から見て理解できる程度の情報を記載
- 「やらないこと」でレビュアーの確認範囲を明確にする
- 「検討した内容」で実装の悩んだ部分や選択理由を残す
- 不要なセクションは削除して OK
- PR 全体で MECE を意識して端的にまとめる
