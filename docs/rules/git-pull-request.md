# プルリクエスト運用ルール

本プロジェクトの PR 運用ルール。レビューフローの効率化と一貫性のため、PR 作成・マージ時は以下に従う。

## マージ条件

- 最低 1 人のレビュー承認が必要
- CI（GitHub Actions）が全て成功している
- コンフリクトが解消されている
- ベースは `develop` ブランチへマージ（`hotfix/*` のみ `main`。[ブランチ運用ルール](./git-branch.md) 参照）
- マージ後はブランチを削除

## 作成フロー

1. リモートに push して PR 作成
2. CI 失敗があれば全て修正
3. Reviewers を追加し、GitHub Copilot レビュー + 人間レビューを通す
4. CodeRabbit のレビューを通す（設定は `.coderabbit.yaml`。PR 作成時に `coderabbit review`（CLI）を実行する）
5. レビュー承認後にマージ（基本 `develop`）

## レビュー指摘対応

レビューの指摘に対応する際は、対応の追跡性とレビュアーの再確認を容易にするため以下に従う。

- **指摘ごとにコミットを分ける**：1 つの指摘対応 = 1 コミット。複数の指摘をまとめてコミットしない。
- **指摘のスレッドにリプライする**：対応した指摘ごとに、該当コミットの **コミット ID** と **対応内容** をそのスレッドへコメントする。CodeRabbit の指摘も同様に扱う。
  - スレッド返信可能なレビューコメント（行に紐づく review comment）は `gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies -X POST -f body='<返信本文>'` でそのスレッドへ返信する。新規の PR コメントとして書き起こさない。
  - 行に紐づかない全体コメント（walkthrough 等）でスレッド返信ができない場合のみ、通常の `gh pr comment` で返信してよい。

## PR テンプレート

実体は `.github/pull_request_template.md`（PR 作成時に GitHub が自動挿入する）。内容は以下と同一に保つ。

````markdown
<!-- type: feat / fix / chore / refactor / test / hotfix -->
<!-- ベースブランチ: 通常は develop（hotfix/* のみ main） -->

## 参照

<!-- 参照しているIssueや関連するプルリクエスト・Issueのリンクを貼る -->

<!-- refs: #123 -->

## ゴール

<!-- 何の機能ができていればゴールか（UI がある場合は、どの画面ができていればゴールか）を書く -->
<!-- 「何を変えたか」の要約は書かない（CodeRabbit が自動でまとめる） -->

## 確認事項

<!-- AI / 作成者向け: マージ前にこの PR 単体で担保できることだけ書く。 -->
<!-- 書いてよい: ローカル動作確認、ローカルUI確認、追加・変更した自動テスト、CI -->
<!-- 書いてはいけない: stg/prd 手動確認、デプロイ後確認、結合テスト計画 -->
<!-- 自動テストの担保・ローカル確認済みは、証拠画像（テスト結果・画面キャプチャ等）があれば添付する（必須ではない） -->

- [ ] バックエンド: 追加・変更した自動テストで動作担保済み（対象外なら N/A）
- [ ] フロントエンド: 追加・変更した自動テストで動作担保済み（対象外なら N/A）
- [ ] ローカルで確認済み（動作、UI がある場合は画面表示も）
  <!-- 何をどう確認したか（テストした操作・入力・画面）を具体的に書く。画像は任意、確認内容の記述は必須 -->
  -
- [ ] CI 通過
````

## 「確認事項」に書いてよいこと / 書いてはいけないこと

PR 本文の「確認事項」は **この PR をマージしてよいかを判断する材料** である。チェックされないまま Close されて意味がない項目（デプロイ後・stg 手動など）は書かない。

| | 内容 |
| --- | --- |
| **書いてよい** | ローカルでの動作確認、ローカルでの UI 確認（画面変更がある場合）、追加・変更した自動テストの通過、CI 通過 |
| **書いてはいけない** | stg / prd での手動確認、デプロイ後の確認、リリース後の結合テスト、本番監視 |

**AI 向け:** PR 本文を作成・編集する際は、セクション名を `## 確認事項`（`動作確認` / `テスト計画` ではなく）とする。マージ前に PR 単体で担保できる検証のみを列挙する（該当する場合はバックエンド/フロントエンドの自動テスト担保を別チェックボックスに分ける、ローカル確認、CI）。stg/prd の手動確認やデプロイ後 TODO をチェックリストに追加しない。ローカル確認項目には、何を確認したか（操作・入力・画面）を必ず具体的に記述する（画像添付は任意）。UI に影響がない PR では動作確認のみで良く、画面確認の記述は不要。自動テスト項目にも有用であれば証拠画像を添付してよい（必須ではない）。

## 記載のポイント

- 簡潔に、しかし後から見て理解できる程度の情報を記載
- 「やらないこと」でレビュアーの確認範囲を明確にする
- 「検討した内容」で実装の悩んだ部分や選択理由を残す
- 不要なセクションは削除して OK
- PR 全体で MECE を意識して端的にまとめる
